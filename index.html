Case study MedicAid (HMS) · Healthcare

Inside MedicAid: one system for every role in the hospital

Problem
Hospitals that run on paper and spreadsheets lose time between departments. The front desk, doctors, nurses, pharmacy, lab and finance each hold a piece of a patient's story, and no one sees the whole of it.
Approach
One system for patient care, admissions and discharges, pharmacy, lab, billing, HR and payroll, and facilities. Each of seven roles lands on its own dashboard and sees only what is relevant to them. A Java Vert.x API on PostgreSQL handles JWT sign-in and checks every request against administrator-managed roles and permissions on the server, and a Vue and Vuetify interface covers the screens. Prescribing is checked against allergies and drug interactions, vitals are scored with NEWS2, bills can be paid by M-PESA STK push and claimed from SHA, patients get their own portal, and a read-only FHIR R4 API exposes records to other systems.
Scale
7 roles · 86 pages · 54 backend services · 73 database tables.
My role
I built the whole system: the Vue and Vuetify frontend, the Java Vert.x backend and the PostgreSQL database design.

Case study School Management System · Education

Inside the School Management System: many schools, one platform

Problem
Schools run admissions, fees, attendance, exams and parent communication across spreadsheets, paper files and messaging apps. A platform that serves many schools also has to keep each school's data strictly apart.
Approach
One multi-tenant platform. Every request enters through a single gateway that verifies the JWT, takes the caller's identity from the verified claims, applies a role check and forwards the request over the Vert.x event bus to the service that owns that domain: admissions, fees, attendance, exams and CBC report cards, timetable, library, hostel, payroll, analytics and more. Payment events are written with a transactional outbox so they cannot be lost. Each school can switch optional modules on or off, administrators can grant or revoke permissions per role, and sign-in supports email OTP and authenticator 2FA. The M-PESA and Paystack integrations run in a simulated mode until provider credentials are configured.
Scale
28 services · 283 processing codes · 39 database migrations · 65 backend and 32 frontend tests.
My role
I built the whole system: the Vue 3, TypeScript and Vuetify frontend, the Java Vert.x backend and the PostgreSQL schema.

Private repository, code on request. Not yet hosted.

Canteen System · Technical note

How the M-PESA payments work

Some dishes must be paid for online first, so a customer who pays must get their food and a customer who does not pay must not. The payments are built on M-PESA STK push through Safaricom Daraja, in Java Vert.x and PostgreSQL.

The flow

The server checks the order is the customer's and the phone number is a valid Safaricom number. It saves the attempt as initiated with a unique reference, then asks Daraja to send the STK prompt to the phone. Only a confirmed result marks the payment captured.

1. The callback is a hint, not proof

Daraja's callback has no signature the server can verify, so anyone who found the address could fake a result. It is only used to look up the payment. The server then asks Daraja's authenticated status endpoint, and that answer decides. A forged callback cannot move money.

2. Assume some callbacks never arrive

A scheduler runs every 60 seconds and re-checks attempts that are still waiting. Attempts with no answer after 15 minutes are marked failed, so the customer can retry. "Still processing" counts as "ask again later", never as a failure.

3. Every step is safe to repeat

A unique reference stops a double-tap from charging twice. Capture only updates a payment that is still waiting, so when the callback, the status check and the scheduler all arrive together, exactly one of them wins.

The code is in a private repository, and I am happy to walk through it.
